# 状态与交互架构原则

> 这份文档记录**为什么**这样设计，而不是这样实现了什么。
> 改代码前先读它；要改这些原则，先改这份文档并说明理由。

## 一、两层状态，语义不重叠

平板要连 N 台 PC，而 Web 端只连一台。把 Web 端的模型直接搬过来会立刻出现
「绿点配三台全离线」这类自相矛盾。解决办法是**明确区分两个层级**：

| 层级 | 表达什么 | 数据源 | 呈现位置 |
|------|----------|--------|----------|
| **当前机器**（单台） | 「我正在对话的这台，连上了吗、数据新吗」 | 该台机器的 mux + HTTP | 顶部状态点、对话页 |
| **每台机器**（全部） | 「每一台各自活着吗」 | 每台的 `SessionMonitor` | 控制台的设备卡 |

**硬性规则：顶部的状态点只代表当前机器，永远不做跨机器汇总。**
每台机器的健康度由它自己的设备卡表达。两个层级各说各的，就不可能打架。

判定「已连接」必须同时满足两个条件，缺一不可：

1. mux（WebSocket）连上了 —— `connected`
2. 最近一次 `session/list` 成功 —— `sessionsOk`

只有 socket 通不算健康。之前的 bug 正是「socket 好着、列表全空」却显示绿色。

## 二、监控是全局的，不是当前机器的

`ServerManager` 对**所有绑定机器**建 `SessionMonitor`，每 8 秒全部轮询一遍。
未读标记、系统通知、完成提示音都在这条路径上触发，因此：

**绑定几台就监控几台、就通知几台。** 不存在「只监控当前机器」的模式。

已知取舍：`api-session/status` 实时推送只覆盖当前机器（mux 只连一台），
所以后台机器「跑完了」这件事最多晚一个轮询周期（8s）被发现。
要消掉这个延迟就得给每台都开 mux，那是 N 条长连接，当前认为不值得。

「跑完了」的判定是**边沿**而非电平：`_prevRunning[id]` 由 true 变 false 才触发，
且**跳过当前会话**——你正看着的会话不需要通知你。

## 三、手势语义唯一

同一个手势必须永远导致同一类结果。曾经的错误设计：

```dart
// 反例：点同一张卡，结果取决于那台机器碰巧有没有在跑会话
if (group.running.isNotEmpty) { onOpenSession(...); } else { onSwitchServer(...); }
```

这直接造成「有时进对话、有时不进」的混乱。正确划分：

| 手势 | 语义 | 结果 |
|------|------|------|
| 点**设备卡** | 切当前机器 | 留在控制台，只改「对话页连哪台」 |
| 点**会话行** | 打开那个会话 | 切机器 + 跳对话页 + 连该会话 |

「切机器」和「打开会话」是两个独立概念，必须由两个不同手势触发。

## 四、切换机器只能有一个入口

`ChatScreen` 的 key 是 `ValueKey(activeServerId)`，所以**改 `activeServerId`
本身就会重建对话页并重新 `boot()`**。

因此**不允许**在改完 `activeServerId` 之后再去调 `switchSession` / 路由请求
——那是同一件事做两遍，必然产生竞态。规则：

- 只切机器 → 只改 `activeServerId`，结束
- 切机器 + 指定会话 → 改 `activeServerId`，**并在同一处**写入目标会话，
  让重建后的 `boot()` 读到它

## 五、状态颜色向 Web 端看齐

Web 端的状态点是**单一问题**：「我的连接活着吗」。平板拆成四态是必要的，
因为平板多了「连上但数据不可信」这一种真实存在的中间态：

| 状态 | 颜色 | 含义 |
|------|------|------|
| connecting | 橙 | 正在建连 |
| healthy | 绿 | socket 通 **且** 数据新鲜 |
| degraded | 橙 | socket 通但接口失败（可点开看原因） |
| offline | 红 | 断开 |

**任何写入状态字段的地方，都必须有地方读它。** 历史上多次出现
「字段被赋值、无人读取」的哑巴字段（`connectionError`、`lastTurnEnd`），
这类字段等于没有。新增状态字段时必须同时接上呈现。

## 六、什么该出现在会话列表里

DSH 在执行任务时会自动拉起**子 Agent 会话**。它们带 `origin == 'subagent'`
和 `parentSessionId`，和用户的对话混在同一个 `session/list` 里返回。

**它们不是用户的对话，一个都不该显示。** Web 端的规则在
`ui-workspace/src/client/tree.ts` 的 `sessionVisible()`：

```ts
session.origin !== 'subagent'
  && !archived.has(session.id)
  && (!session.blank || session.id === current)
```

App 端用 `utils/session_format.dart` 的 `isUserFacingSession()` 表达前两项
（归档由各调用方的 `archivedIds` 处理）。

**硬性规则：过滤必须发生在数据入口，不能只在 UI 层挡。**

理由不只是「列表要干净」：`SessionMonitor.refresh()` 在同一次循环里做
未读标记和**完成通知**。如果子 Agent 留在数据里，那么任何一个子 Agent
跑完都会弹「会话已完成」并响提示音——用户会在完全无关的时刻被打扰。

因此 `SessionMonitor` 和 `ChatController` 两处 `listSessions()` 的返回值
都必须过这一层。新增任何消费 `session/list` 的地方，同样要过。

## 七、重构不得静默删除功能

这个仓库发生过一次大规模重构，把控制台的「最近 3 小时 / 全部已读 / 未读橙标 /
设备徽章 / 下拉刷新」、对话页的「停止 / 变更入口 / 重连 / 断线横幅」、
以及整条「未读 + 通知 + 提示音」链路**全部删掉且无人察觉**，
表现成「之前是有的，现在没了」。

规则：

- 重写一个文件前，先 `git show HEAD:<file>` 看清它有哪些能力
- 覆盖前逐项确认：这个能力在新实现里由谁承担
- 拿不准就保留，不要删
- 提交前用 `git diff --stat HEAD` 扫一遍异常缩水的文件
